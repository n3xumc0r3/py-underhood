# Часть XV. От .py к байт-коду: компиляция и виртуальная машина

Часть VIII показывала внутренности CPython через готовые объекты: фреймы (8.4), `__code__` (8.7), `dis` как дизассемблер (8.9). Здесь — два недостающих этажа ниже и выше: **как исходник становится байт-кодом** (пайплайн компилятора и формат `.pyc`) и **что исполняет этот байт-код** (виртуальная машина, её специализации и GIL). Все примеры проверены на CPython 3.12; там, где поведение зависит от версии, это оговорено.

## 15.1. Почему Python и компилируется, и интерпретируется { #15.1 }

Вопрос «Python — компилируемый или интерпретируемый язык?» построен на ложной дихотомии. Компиляция — свойство **трансляции**: исходник переводится в другое представление. Интерпретация — свойство **исполнения**: кто выполняет это представление. CPython делает и то, и другое: сначала компилирует исходник в байт-код, затем интерпретирует байт-код в цикле виртуальной машины (15.5). Java устроена так же; C компилирует в машинный код, который исполняет уже процессор; у bash стадия компиляции вырождена — интерпретатор ходит по исходнику почти напрямую.

Почему не компилировать сразу в машинный код, как C? Потому что в Python ключевая информация известна только в рантайме. Для `x * 2` нельзя выбрать машинную инструкцию умножения: `x` может быть int, float, str, списком, объектом с `__mul__` — и ещё измениться до исполнения. Имена и атрибуты разрешаются в момент обращения, код может появляться во время работы программы (`exec`, `input` → `eval`, интерактивная сессия). Статическая компиляция либо потеряла бы часть семантики языка, либо превратила бы каждый оператор в пачку типовых проверок — что, впрочем, и происходит дальше в этой части: только проверки эти **рантайм-наблюдаемые**, а не зафиксированные при компиляции.

Компиляция происходит не один раз и не в одном месте:

- **при `import` модуля** — и результат кэшируется в `.pyc` (15.2);
- **при запуске скрипта** — компилируется весь файл целиком, до исполнения первой строки;
- **в REPL и в `exec`/`eval`** — компилируется каждый введённый блок.

Третье следствие первой строки списка — любимый сюрприз новичков:

```text
$ cat broken.py
print("первая строка")
def broken(:        # незакрытая скобка
$ python broken.py
  File "broken.py", line 2
    def broken(:        # незакрытая скобка
               ^
SyntaxError: invalid syntax
```

`print` стоит выше ошибки, но «первая строка» не успела выполниться: скрипт компилируется целиком, и `SyntaxError` поднимается раньше, чем интерпретатор приступил к исполнению. (В REPL всё иначе — каждый блок компилируется отдельно, поэтому ранее введённые строки уже исполнены.)

Миф о `.pyc`, который стоит развеять сразу: наличие файла байт-кода **не ускоряет исполнение кода**. Экономится только парсинг и компиляция при импорте — один проход на процесс, а не на каждую инструкцию. И `.pyc` — не защита кода: декомпиляция усложнилась, но `dis` (8.9) всё равно читает байт-код напрямую.

Наконец, байт-код — промежуточное представление (IR): компактное и переносимое между машинами одной архитектуры, но **не между версиями Python** — набор опкодов меняется от версии к версии, и именно это фиксирует magic number в заголовке `.pyc` (15.2).

## 15.2. Импорт и .pyc: формат, кэширование, инвалидация { #15.2 }

При `import demo_mod` конвейер выглядит так: механизмы импорта находят модуль (finders), `SourceFileLoader` читает исходник, компилирует его `compile()` и исполняет в отдельном пространстве имён; результат кэшируется в `sys.modules` — второй `import` того же модуля уже ничего не читает и не исполняет. Компиляция — дорогая часть конвейера, и ради неё кэш: рядом с исходником появляется `__pycache__`:

```python
# в каталоге модуля после первого import:
# __pycache__/demo_mod.cpython-312.pyc

import sys, importlib.util
sys.implementation.cache_tag      # 'cpython-312'
importlib.util.MAGIC_NUMBER       # b'\xcb\r\r\n'
```

Имя файла — `имя_модуля` + `cache_tag`: на одной машине спокойно живут pyc для 3.11 и 3.12 рядом. Первые 16 байтов файла — заголовок, читаемый на пальцах через `struct.unpack("<4sIII", header)`:

| Поле | Размер | Что содержит |
|---|---|---|
| magic | 4 байта | `b'\xcb\r\r\n'`: 2 байта номера формата байт-кода + `\r\n` (артефакт эпохи текстовых трансферов — чтобы бинарник не портили SMTP/FTP-шлюзы) |
| бит-поле | 4 байта | `0` — timestamp-based; `1`/`3` — hash-based (PEP 552) |
| поле 3 | 4 байта | mtime исходника (timestamp-вариант) или первые 4 байта хеша |
| поле 4 | 4 байта | размер исходника (или вторые 4 байта хеша) |

Дальше заголовка — marshalled code object модуля. Magic number — это про **совместимость байт-кода**: набор опкодов меняется между версиями, поэтому pyc от 3.12 не загрузится в 3.11 — та классическая ошибка `bad magic number` означает «файл скомпилирован не тем интерпретатором».

Инвалидация по умолчанию — по mtime и размеру исходника: если они совпали с записанными в заголовке, pyc считается свежим. Для контейнеров и деплоя, где mtime ненадёжен, PEP 552 добавил hash-based pyc:

```python
import py_compile
py_compile.compile("demo_mod.py",
                   invalidation_mode=py_compile.PycInvalidationMode.CHECKED_HASH)
# бит-поле в заголовке станет 3; вместо mtime — 8 байт хеша исходника
```

`checked_hash` проверяет хеш при каждом импорте; `unchecked_hash` верит файлу на слово — быстрее, но кэш никогда не инвалидируется сам. Режим проверки при старте переключается флагом `--check-hash-based-pycs always|default|never`: `always` — валидировать все hash-pyc, `never` — доверять всем без чтения исходника, `default` — по бит-полю (`checked_hash` проверяет, `unchecked_hash` — нет). Сам хеш — siphash13 от содержимого исходника с ключом — магическим числом формата pyc (`_RAW_MAGIC_NUMBER`, например `3531` для 3.12); так чужой интерпретатор с другим magic number не примет чужой pyc. Проверить можно через `_imp.source_hash(magic, source)` — функция возвращает 8 байт. `PYTHONHASHSEED` здесь ни при чём — он управляет рандомизацией хешей `str`/`bytes`, а не pyc (PEP 552). Разовые утилиты: `py_compile.compile()` для одного файла, `compileall` — для дерева каталогов. Окружение тоже влияет: `PYTHONDONTWRITEBYTECODE` (или `sys.flags.dont_write_bytecode`) запрещает создавать pyc вообще, `PYTHONPYCACHEPREFIX` уводит весь кэш в один общий каталог — удобно для деревьев исходников на read-only ФС.

Две детали, о которых часто не догадываются. Первая: **main-скрипт не кэшируется** — запустите скрипт, импортирующий модуль, и загляните в `__pycache__`: там лежит pyc только модуля. Скрипт компилируется на каждом запуске; экономить нечего — он исполняется один раз за процесс. Вторая: декомпиляция pyc — это не симметричная операция. Инструменты (uncompyle6, decompyle3) полноценно работают примерно до 3.8; на актуальных версиях байт-код усложнился (специализации, кэши, таблицы исключений), и декомпиляторы отстают. «Отдам только pyc» сегодня защищает лучше, чем пять лет назад, — но байт-код всё равно читается вручную через `dis`, так что стратегией защиты кода это называть нельзя.

## 15.3. Пайплайн компилятора: токены → PEG → AST → байт-код { #15.3 }

Между исходником и байт-кодом — четыре станции. Токенизатор режет текст на лексемы (учитывая кодировочную декларацию, 9.1). Парсер строит дерево. Компилятор обходит дерево, составляет таблицу символов (кто local, кто free, кто global — именно здесь рождаются cell-объекты замыканий, 8.3) и генерирует байт-код в виде CFG — графа базовых блоков, который превращается в линейный поток инструкций плюс таблицы исключений.

С версии 3.9 парсер — PEG (PEP 617): грамматика языка описана в PEG-нотации в `Grammar/python.gram`, а прежний LL(1)-парсер с его «хаками» (токен-буфер, специальные случаи в лексере) отправлен на пенсию. Практическое следствие: у PEG-парсера нет ограничений LL(1), и грамматику стало проще расширять — часть новых синтаксисов (pattern matching) обязана этому удобству.

Официальное окно в дерево — модуль `ast`:

```python
import ast
print(ast.dump(ast.parse("x = a + b"), indent=2))
```

```text
Module(
  body=[
    Assign(
      targets=[
        Name(id='x', ctx=Store())],
      value=BinOp(
        left=Name(id='a', ctx=Load()),
        op=Add(),
        right=Name(id='b', ctx=Load())))],
  type_ignores=[])
```

Сравните с исходником: скобок и приоритетов больше нет — они превратились в структуру вложенности; контекст каждого имени явный (`Store` — цель присваивания, `Load` — чтение). Именно по этому дереву ходят линтеры и форматтеры; ruff (12.7) использует своё AST на Rust, mypy — своё, но идея одна: править или анализировать код на уровне дерева, а не строк. Родственная утилита `symtable` показывает таблицу символов — то же дерево глазами компилятора.

На уровне AST происходит и первый этап оптимизаций — свёртка констант:

```python
import dis
dis.dis(compile("x = 2 ** 10", "<s>", "exec"))
#      2 LOAD_CONST               0 (1024)      ← посчитано при компиляции
#      4 STORE_NAME               0 (x)
```

Свёртка имеет пределы разумности: `2 ** 10000` в константу **не** сворачивается — в байт-коде останутся `LOAD_CONST 2`, `LOAD_CONST 10000` и `BINARY_OP **`. Компилятор не должен тратить время сборки на вычисление гигантских чисел (а байт-код — носить их в себе), поэтому границы свёртки ограничены. Это же поведение упоминалось в 8.2 как источник сюрпризов с `is` на константах.

Вторая инфраструктурная новинка — **таблицы исключений** (3.11+). Раньше `try/except` компилировался в явные инструкции `SETUP_FINALLY`, исполнявшиеся на каждом входе в блок. Теперь вход в `try` бесплатен: информация «какой обработчик ловит какой диапазон байт-кода» вынесена в отдельную таблицу `co_exceptiontable`, которую VM читает только в момент исключения:

```python
def t():
    try:
        return 1
    except ValueError:
        return 2

len(t.__code__.co_exceptiontable)   # 8 — байты разметки для VM
```

Попутно PEP 657 научил трейсбеки показывать точный фрагмент выражения, а не целую строку — разметка для этого тоже живёт в таблицах.

Публичный вход во весь пайплайн — функция `compile(source, filename, mode)`: режимы `exec` (набор инструкций), `eval` (одно выражение), `single` (REPL-блок с печатью результата). Готовый code object исполняется `exec`-ом многократно дешевле, чем повторный `compile` строки — в цикле разница видна на микробенчмарках. И `compile` — дешёвый «линкер-проверка»: он ловит `SyntaxError` до исполнения, не запуская ни одной строки кода.

## 15.4. Стековая машина: как читается байт-код { #15.4 }

Байт-код CPython — **wordcode** (с 3.6): каждая инструкция — чётное число байтов, минимум два: байт opcode и байт oparg. Безоперандные инструкции oparg игнорируют. Разбор начнём с простой функции:

```python
def f(a, b):
    return a * b + 2

import dis
dis.dis(f)
```

```text
  1           0 RESUME                   0

  2           2 LOAD_FAST                0 (a)
              4 LOAD_FAST                1 (b)
              6 BINARY_OP                5 (*)
             10 LOAD_CONST               1 (2)
             12 BINARY_OP                0 (+)
             16 RETURN_VALUE
```

Левый столбец — номер строки исходника (для трейсбеков), второй — **смещение в байтах** от начала `co_code`, то есть индекс инструкции, умноженный на 2. Промежутки между смещениями — встроенные кэши (ниже). Исполнение идёт над **стеком операндов**: глубина известна компилятору заранее и записана в `co_stacksize` (здесь `2` — максимум два значения одновременно):

| Инструкция | Стек до → после | Смысл |
|---|---|---|
| `LOAD_FAST 0 (a)` | `[]` → `[a]` | локальная №0 (`co_varnames[0]`) на стек |
| `LOAD_FAST 1 (b)` | `[a]` → `[a, b]` | локальная №1 на стек |
| `BINARY_OP 5 (*)` | `[a, b]` → `[a*b]` | снять два, умножить, положить результат |
| `LOAD_CONST 1 (2)` | `[a*b]` → `[a*b, 2]` | константа №1 из `co_consts` |
| `BINARY_OP 0 (+)` | `[a*b, 2]` → `[a*b+2]` | снять два, сложить |
| `RETURN_VALUE` | `[...]` → `[]` | вернуть вершину стека |

Имена и константы не встречаются в инструкциях как текст — только как **индексы** в таблицах code object: `co_varnames=('a', 'b')`, `co_consts=(None, 2)`, `co_names=()` (глобальных имён функция не трогает; подробнее о code object — 8.7). Сырые байты видны в `co_code`:

```python
f.__code__.co_code
# b'\x97\x00|\x00|\x01z\x05\x00\x00d\x01z\x00\x00\x00S\x00'
#  97 00 — RESUME;  7c 00 — LOAD_FAST a;  7c 01 — LOAD_FAST b;
#  7a 05 — BINARY_OP *;  00 00 — кэш-слово;  64 01 — LOAD_CONST 2;
#  7a 00 — BINARY_OP +;  00 00 — кэш-слово;  53 00 — RETURN_VALUE
```

18 байтов на шесть «настоящих» инструкций: с 3.11 поток байт-кода вперемешку с **кэш-словами** — нулевыми заполнителями, которые VM после прогрева записывает данными для быстрой инструкции (15.5). В свежескомпилированном `co_code` они нули.

Микро-деталь из дизассемблера: `RETURN_CONST` (3.12+) — возврат константы одним опкодом вместо пары `LOAD_CONST` + `RETURN_VALUE`. На таком уровне язык байт-кода продолжает чиниться от версии к версии — ещё одна причина, почему magic number строгий.

Генераторы выглядят в байт-коде заметно иначе (механика генераторов — Часть III):

```python
def g():
    yield 1

dis.dis(g)
```

```text
  1           0 RETURN_GENERATOR
              2 POP_TOP
              4 RESUME                   0

  2           6 LOAD_CONST               1 (1)
              8 YIELD_VALUE              1
             10 RESUME                   1
             12 POP_TOP
             14 RETURN_CONST             0 (None)
        >>   16 CALL_INTRINSIC_1         3 (INTRINSIC_STOPITERATION_ERROR)
             18 RERAISE                  1
ExceptionTable:
  4 to 14 -> 16 [0] lasti
```

Первые же инструкции объясняют, почему вызов `g()` не исполняет тело: `RETURN_GENERATOR` возвращает генератор-объект **до** входа в тело функции. `RESUME` — точка, с которой VM продолжает исполнение после каждого `yield` (аргумент отличает первичный вход от возобновления). Хвост с `CALL_INTRINSIC_1 (INTRINSIC_STOPITERATION_ERROR)` — разметка для случая, когда генератор завершается `return`: обычный `StopIteration` надо превратить в ошибку «generator raised StopIteration» (PEP 479). А блок `ExceptionTable:` внизу — та самая таблица исключений из 15.3, здесь она размечает, куда идти при ошибке внутри `yield`. Формат строки: `start to end -> target [index] lasti` — `start`/`end` диапазон байт-кода, `target` точка перехода, `index` (здесь `[0]`) — индекс обработчика в таблице стека, `lasti` означает «использовать `f_lasti` для восстановления позиции».

## 15.5. Виртуальная машина: eval loop, специализация, GIL, JIT { #15.5 }

Исполнением байт-кода занимается eval loop — вечный цикл в `Python/ceval.c`: прочитать инструкцию, декодировать, исполнить в гигантском `switch`, повторить. Стек фреймов (8.4) задаёт контекст — локальные переменные, стек операндов, точку возврата; сам цикл общий для всего потока. Это и есть «виртуальная машина»: программная машина с собственным набором инструкций, исполняемая поверх реальной.

С 3.11 этот цикл стал **адаптивно специализирующимся** (PEP 659). Идея: пока типы неизвестны — исполнять универсальную инструкцию, но считать её исполнения; после прогрева VM смотрит, какие типы проходили через инструкцию, и **заменяет** её в потоке байт-кода на специализированный вариант. То, что вычисляет `f(2, 3)` после тридцати вызовов с int:

```python
dis.dis(f, adaptive=True)   # тот же f из 15.4, после прогрева int'ами
```

```text
  1           0 RESUME                   0

  2           2 LOAD_FAST__LOAD_FAST     0 (a)
              4 LOAD_FAST                1 (b)
              6 BINARY_OP_MULTIPLY_INT     5 (*)
             10 LOAD_CONST               1 (2)
             12 BINARY_OP_ADD_INT        0 (+)
             16 RETURN_VALUE
```

`BINARY_OP` превратился в `BINARY_OP_MULTIPLY_INT` — без проверки типов и без диспетчеризации через protocol; соседние `LOAD_FAST` склеились в суперинструкцию `LOAD_FAST__LOAD_FAST`. Опкод в потоке байт-кода — то есть в самом code object — **физически заменён**. Если через инструкцию пойдут другие типы, специализация провалится и вернёт универсальный вариант (deopt).

Для атрибутов и операций, чья скорость зависит не только от типа, но и от истории объекта, специализация работает в паре с **инлайновыми кэшами** — теми самыми кэш-словами из 15.4:

```python
class P:
    def __init__(self):
        self.x = 1
    def get(self):
        return self.x

p = P()
for _ in range(30):
    p.get()

dis.dis(p.get, adaptive=True, show_caches=True)
```

```text
  4           0 RESUME                   0

  5           2 LOAD_FAST                0 (self)
              4 LOAD_ATTR_INSTANCE_VALUE     0 (x)
              6 CACHE                    0 (counter: 832)
              8 CACHE                    0 (version: 131482)
             10 CACHE                    0
             12 CACHE                    0 (keys_version: 0)
             14 CACHE                    0
             16 CACHE                    0 (descr: 0)
             18 CACHE                    0
             20 CACHE                    0
             22 CACHE                    0
             24 RETURN_VALUE
```

(числа в кэшах — runtime-значения конкретного прогона). `LOAD_ATTR_INSTANCE_VALUE` — быстрый путь для атрибута в `__dict__` обычного объекта; кэш хранит счётчик прогрева, версию типа и дескриптор. Пока версия типа не изменилась (никто не трогал класс и его атрибуты), обращение к атрибуту — почти доступ по смещению. Добавьте в класс атрибут во время исполнения — версия устареет, кэш недействителен, инструкция вернётся к универсальному `LOAD_ATTR`. Отсюда же берутся сюрпризы из 8.5: на 3.11+ счётчики и «магия» вокруг объектов ведут себя иначе, потому что код исполняется по другим путям.

Ускорение этой линейки — измеримое: 3.11 даёт в среднем порядка 1.25× на стандартном наборе бенчмарков против 3.10, часть этой работы — специализации. Следующий шаг — JIT (PEP 744, с 3.13): экспериментальный, copy-and-patch (техника, где готовые куски машинного кода (stencil) копируются и «пачкаются» (patch) подставкой конкретных аргументов), включается при сборке интерпретатора; «горячий» код после всех специализаций компилируется в машинный код. Статус на текущую версию — в whatsnew конкретного релиза: эта часть книги про 3.12, где JIT ещё нет, а специализации — главный движок скорости.

Про **GIL** в этих терминах: глобальная блокировка интерпретатора — это «один eval loop на процесс», то есть байт-код одного потока исполняется в каждый момент только одним потоком. Потоки переключаются не по тикам счётчика инструкций, а по времени: раз в `sys.getswitchinterval()` секунд (по умолчанию 0.005) активный поток сдаёт GIL. Свободная от GIL сборка (PEP 703, экспериментальная с 3.13) — это буквально сборка интерпретатора, где GIL убран как единая глобальная блокировка, а критические секции перенесены на уровень объектов (biased reference counting + refcount-aware C-API); плата — overhead на счётчиках ссылок и требование, чтобы C-расширения были к этому готовы.

Заглянуть в живую машину можно из Python: `sys.settrace`/`sys.setprofile` (отладчики и профайлеры сидят именно на этих крючках, поднимаемых между инструкциями) и audit hooks (10.7) — события уровня C API, независимо от того, какой опкод их породил.

### Бенчмарки к Части XV { #15.5-benchmarki }

```python
# exec строки vs code object в цикле (CPython 3.12):
import timeit
code = compile("x = 1 + 2", "<bench>", "exec")
timeit.timeit(lambda: exec(code), number=100_000)          # ≈ 0.02 с
timeit.timeit(lambda: exec("x = 1 + 2"), number=100_000)   # ≈ 0.56 с
# повторный compile строки дороже в ~26 раз
```

Числа ориентировочные: абсолютные значения зависят от машины, отношение — нет. Вывод практический: если шаблон кода исполняется многократно — `compile` один раз, `exec` много раз.
