# Контрибьют в «Python под капотом»

Спасибо, что хотите помочь книге! Этот документ объясняет, как устроены правки, какой стиль принят, и что нужно знать перед отправкой PR.

## Коротко

1. Опечатки, битые ссылки, фактические ошибки — открывайте PR напрямую.
2. Большие новые секции / переписывание существующих — сначала откройте issue для обсуждения.
3. Все правки делаются под двойную лицензию проекта (см. раздел «Лицензия контрибьюций» ниже).
4. Перед PR проверьте, что локально собирается MkDocs: `mkdocs serve` — книга должна открыться на http://127.0.0.1:8000 без ошибок.

## Стиль

### Markdown

- Заголовки глав — `# Часть N. Название` (H1, один на файл).
- Подразделы внутри главы — `## N.M. Название` (H2). Под-подразделы — `###`.
- Внутри одной главы **не должно быть второго `#` H1** — MkDocs Material автоматически строит right-side TOC из H2/H3.
- Биты кода — три бэктика с языком: ` ```python `, ` ```bash `, ` ```text `. Не используйте ` ```plain ` — подсветка не сработает.
- ⚠️ — символ для «подводных камней». Используйте его в начале блока `> ⚠️ **Внимание:** ...` — так исторически сложилось в книге.
- Ссылки на другие главы — относительные: `[см. Часть III](03-generators.md)`. Не используйте `.html` — MkDocs сам подставит.
- Длинные строки можно оставлять как есть (MkDocs их переносит), но в пределах абзаца ставьте один перенос строки.

### Python-код в сниппетах

- Python 3.10+ как baseline. Если используется фича 3.11+ — отмечайте в комментарии: `# Python 3.11+: asyncio.TaskGroup`.
- PEP 8 — обязательно, но trailing comma в multi-line вызовах желательна.
- Если в примере есть `print(...)` с русским текстом — убедитесь, что кириллица не ломается в шрифтах Material (обычно не ломается).
- Не используйте `# -*- coding: utf-8 -*-` — это Python 2 стиль, в 3+ не нужно.
- emoji в коде — только если они часть строки (например, в `print("⚠️ внимание")`).

### Тон

- Книга написана от первого лица множественного («мы видим», «мы используем») или безлично («функция возвращает»). Не ломайте эту интонацию.
- Примеры реального кода — с комментарием `# плохо:` / `# хорошо:` или `# длинно:` / `# короче:` — это устоявшийся приём.
- Не бойтесь длинных примеров (30–50 строк) с подробными комментариями — это конспект, не блогпост.

## Локальная сборка

```bash
git clone https://github.com/n3xumc0r3/py-underhood.git
cd py-underhood
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
mkdocs serve
# открыть http://127.0.0.1:8000
```

## Логика правок

### Что мержится без вопросов

- Опечатки в тексте и в коде.
- Битые ссылки (на PEP, на внешние ресурсы, на внутрикнижные разделы).
- Фактические ошибки: неверная версия Python, неверное описание API, устаревший PEP.
- Улучшение формулировок без изменения смысла.
- Дополнение примеров — если пример лучше существующего.

### Что требует обсуждения (issue first)

- Новые подразделы (1.26, 5.18, и т.д.).
- Перестановка разделов местами.
- Удаление существующего контента.
- Переписывание раздела «с нуля».

### Что не мержится

- Плагиат — копирование абзацев из Real Python, Хабра, других книг. Если цитируете — оформляйте как цитату со ссылкой.
- Рекламные ссылки «added useful resources» без отношения к теме.
- Стилистические переписывания под «свой голос» — книга должна звучать одинаково.

## Лицензия контрибьюций

**Открывая PR, вы подтверждаете:**

1. Ваш вклад — оригинальная работа, не скопированная из других источников (книг, статей, блогов), на которые у вас нет прав.
2. Если вы цитируете чужой материал — он оформлен как цитата со ссылкой, и объём цитирования попадает под fair use.
3. Ваш вклад лицензируется под те же условия, что и проект:
   - **Проза** — [CC BY-NC-SA 4.0](LICENSE)
   - **Код** — [MIT](CODE_LICENSE)
4. CLA (Contributor License Agreement) не требуется — делая PR, вы неявно принимаете лицензию проекта. Это та же модель, что у [HackTricks](https://github.com/HackTricks-wiki/hacktricks).

Если вы хотите внести вклад под другой лицензией — это нужно обсудить отдельно (например, код под Apache 2.0 вместо MIT). По умолчанию — нет.

## Процесс review

1. PR открывается с заполненным шаблоном (см. `.github/PULL_REQUEST_TEMPLATE.md`).
2. CI прогоняет `mkdocs build --strict` — если есть ошибки в структуре markdown или битые ссылки, PR не пройдёт.
3. Ревью — в течение 1–7 дней. Возможно, попросят уточнения или изменения.
4. Мерж — squash & merge, чтобы история коммитов оставалась чистой.
